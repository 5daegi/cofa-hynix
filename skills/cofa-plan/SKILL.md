# 요구사항을 실행 가능한 계획으로 바꾸기

실제 과제 지침과 사용자가 확정한 목표를 우선한다. 읽기와 계획만 요청받았다면 파일 생성·설치·구현은 하지 않는다. 계획과 실행까지 요청받았다면 중요한 미확정 결정만 확인한 뒤 진행한다. 제출 후 AI 이용 금지 문답 단계에는 적용하지 않는다.

## 1. 현재 상태 확인

- README와 과제 자료, 폴더, 런타임·패키지 설정, 제출 조건을 확인한다. 관련 파일부터 읽고 전 저장소를 불필요하게 반복 탐색하지 않는다.
- **README만 있는 경우:** 필수 결과물·입출력·실행 환경부터 정한다. 웹앱, API, 데이터베이스, 특정 언어, 패키지 설치가 필요하다고 가정하지 않는다. 기술 선택이 확정되면 입력부터 결과까지 이어지는 가장 작은 기능을 먼저 계획한다.
- **기존 코드가 있는 경우:** 현재 구조·공개 인터페이스·기존 테스트를 확인한다. 실행 가능한 기존 검사를 통해 기준 상태를 파악하고, 기존 실패와 이번 수정으로 생긴 실패를 구분한다. 전면 재작성보다 요구를 충족하는 변경을 먼저 검토한다.

## 2. 판단이 필요한 조건 구분

확정 사실, AI의 제안·추정, 미확정 사항을 분리한다. 문서나 코드로 확인할 수 있는 내용은 먼저 확인한다.

업무 결과를 바꾸는 모호함에 대해서만 질문한다. 질문에는 '무엇이 불명확한지 / 답에 따라 무엇이 달라지는지'를 붙인다. 우선순위가 높은 질문부터 최대 3개씩 묶는다. 담당자에게 보낼 문장은 작성할 수 있지만 실제 전송과 답변 전달은 사람이 한다.

이미 선택한 언어·범위·실행 방식을 다시 승인받지 않는다. 답을 받기 전에는 정책 의존 작업을 미결정으로 남기고, 정책과 독립적인 준비는 요청 범위 안에서 진행한다. 기한이 촉박해도 업무 규칙을 조용히 확정하지 않는다.

## 3. 대안과 최소 계획

중요한 미확정 기술 선택이 있다면 적합한 대안 1~2개를 요구 충족, 의존성, 구현·검증 부담, 남는 한계로 비교한다. 유일하게 적합한 방식이 있으면 이유를 말한다. 이미 위임받은 선택은 근거와 함께 결정하고 사용자 결정으로 가장하지 않는다.

계획은 다음 형태로 작성한다. 작은 과제는 답변 안의 표로 충분하며 별도 설계 문서를 강제하지 않는다.

1. **목표·필수 결과물·제약:** 짧게 정리한다.
2. **사람의 미결정 사항:** 없으면 없다고 표시한다.
3. **기능 단위 작업표:** 목적 / 관련 파일 / 완료 기준 / 검증 / 선행 조건을 적는다.
4. **필수 범위와 선택 범위:** 필수 요구사항을 최소 구현이라는 이유로 제외하지 않는다.
5. **시간 배분과 위험:** 실제 남은 시간에 맞춰 검증·제출 여유를 남긴다.

변수명이나 파일 한 개마다 작업을 쪼개지 않는다. 독립적으로 결과를 판정할 수 있는 기능 단위로 나눈다. 기존 구조가 있다면 유지하고, 새 구조라면 작동하는 첫 경로부터 만든다.

## 4. 검증과 인계

기대 결과는 README·확정된 정책·원본 데이터로 정한다. AI가 작성한 구현 자체를 정답으로 사용하지 않는다. 정상 사례, 핵심 실패 사례, 중요한 경계 사례를 계획에 연결한다. 실제 프로젝트에 존재하는 명령을 확인하며, 없는 명령은 앞으로 만들 계획임을 표시한다.

계획과 명세를 한 번 대조해 빠진 필수 요구, 인터페이스 불일치, 확인되지 않은 가정을 수정한다. 합의된 계획의 실행이 이미 허가되어 있다면 다시 '진행할까요?'라고 묻지 않는다. 중요한 결정이 남았다면 그 항목만 확인하고 독립 작업을 계속한다.

서브에이전트, 별도 worktree, 커밋, PR, 다른 스킬 설치를 필수 단계로 만들지 않는다. 본 스킬은 단독으로 사용할 수 있다.
